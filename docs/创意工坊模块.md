# 创意工坊模块（Creative Workshop）

本项目除了「独立离线 HTML 工具」，也打包成 **Lumina Studio 2 的创意工坊模块**，
可用「创意工坊 → 安装本地模块包」或「从 GitHub Release 安装」装入。

## 为什么两种形态能并存

官方模块包 `.lumina-workshop` 就是一个 ZIP，主体是**单个自包含 HTML**
（官方那个 `lumina.bead-pattern` 的 `ui/index.html` 是 300 KB）。
本项目的工具本来就是单文件、零外部资源，所以**同一份 HTML 同时是独立工具和模块入口**。

## 包结构（官方硬性规则）

ZIP 根目录**只能**包含：

```text
manifest.json
ui/index.html
assets/icon.png
assets/gallery/*        （可选，≤20 张静态 PNG/JPEG/WebP）
README.md
LICENSE
```

不允许：额外 JS 文件、source map、符号链接、重复或大小写冲突路径、路径穿越、
加密成员、动画图片、压缩炸弹。`ui/index.html` 必须完全内联
（JS/CSS/图片都用内联脚本、样式、`data:` 或 `blob:`），`<head>` 必须在第一个
`<script>` 之前，禁用 `eval`、`new Function`、动态 `import()`。

## 打包

```bash
node workshop/build.cjs
```

产出 `workshop/dist/`：

```text
manifest.json
ui/index.html
assets/icon.png
README.md
LICENSE
xwnxzz.handfill-cards-1.1.0.lumina-workshop
xwnxzz.handfill-cards-1.1.0.lumina-workshop.sha256    （小写 SHA-256）
```

构建是**可复现**的：ZIP 用固定时间戳与 STORE，不压缩、不写外部属性。

## 宿主适配层

`workshop/shim.js` 在构建时内联进 `ui/index.html`（`</body>` 之前），只做两件事：

1. **独立浏览器**：`window.parent === window` → 立即返回，行为与原来完全一致，
   不触发任何宿主逻辑
2. **Lumina 沙箱 iframe**：按公开协议握手并接入

### 协议实现（自行实现，未复制 SDK 源码）

官方 SDK `@lumina/workshop-sdk` 是 **GPL-3.0-or-later**。把它打进模块会让整个产物
感染 GPL，所以本模块按**公开协议自行实现**了最小客户端，保持本项目 MIT。

协议依据是官方公开仓库 `lumina-layer-studio/Lumina-Workshop-SDK` 的
`src/contracts.ts`（类型契约）与 `docs/module-development.md`（开发指南）：

| 步骤 | 内容 |
|---|---|
| 1 | 模块向 `window.parent` 发 `{type:"lumina.workshop.ready", moduleId, moduleVersion, apiVersion:"1.0.0", events:["ui.stateChanged"]}` |
| 2 | 宿主回一条 `{type:"lumina.workshop.connect", sessionId, ports:[MessagePort]}` |
| 3 | 之后走 RPC 信封 `{protocol:"lumina-workshop-rpc", version:1, kind:"request"\|"response"\|"event", requestId, method, payload}` |
| 4 | 超时：默认 30 s、`image.pick` 300 s、`handoff.image` 120 s；握手须在 iframe load 后 10 s 内完成 |

### 与宿主交换什么

- **主题 / 语言**：`ui.stateChanged` 事件或 `ui.getState()` 响应 →
  写 `documentElement.lang` 与 `data-theme`，并把 `--lumina-*` 令牌映射到本工具的
  CSS 变量（`--lumina-accent` → `--acc` 等）；宿主深色主题映射到工具的 `.dark` 类。
  非法令牌名（不匹配 `--lumina-[a-z0-9-]+`）一律忽略。
- **交接**：右下角「把当前板面图交给 Lumina」按钮 →
  `handoff.image({ pngBytes, pixelWidth/Height, recommendedWidthMm/HeightMm,
  preserveCanvasBounds:true, layout, colorLibraryId, recipeSource })`

交接用的物理尺寸与网格节距全部取自实测/官方规格，不是估计值：

| 板面 | 物理尺寸 | 网格 | 节距 |
|---|---|---|---|
| 梯度卡 | 67 × 34 mm | 3 行 × 6 列 | 11 mm（block 10 + gap 1） |
| 校准板 | `2×5.0 + total×5.0 + (total−1)×0.8` mm | `total × total` | 5.8 mm |

（校准板的 `margin = 5.0` 取自官方公开 `core/calibration.py` 里六个板生成函数的一致取值。）

### 权限（只申请实际使用的两项）

| 权限 | 用途 |
|---|---|
| `project.storage` | 保存 / 恢复手工测量的色块数据 |
| `handoff.image` | 把确认后的板面图交给 Lumina 转换打印 |

**没有**申请 `image.pick`（手工测量不需要读图）与 `color-library.read`（暂未使用）——
官方指南明确要求「没有申请未使用权限」。

### 已处理的沙箱差异

- `localStorage` 在 `sandbox="allow-scripts"` 的 iframe 里会抛 `SecurityError`。
  工具的持久化本来就包在 `try/catch` 里，宿主内会安全退化为内存保存。
- 下载会被桌面宿主拦截。宿主内请用右下角的**交接按钮**，不要用「导出图片」。

## 两个版本的分工

同一个工具发**两份产物**，因为两者的能力边界不同：

| | 独立版 `lumina_singlestage_gui.html` | 插件版 `.lumina-workshop` |
|---|---|---|
| 打开方式 | 双击浏览器打开 | 创意工坊安装 |
| 导出 CSV | ✅ | ❌ 沙箱拦下载 |
| 导出板面图 PNG / ZIP | ✅ | ❌ 同上 |
| **导入** CSV | ✅ | ✅（本地文件读取不受限） |
| 把板面图交给 Lumina | — | ✅ 白底板 / 黑底板 / 校准板当前页 |
| 触发 Lumina 的「梯度卡提取 / LUT 提取」 | — | ❌ **API 不允许**（见下） |
| 测量数据留存 | 浏览器本地存储 | 模块工程存储（`project.storage`） |

插件版会**隐藏那 8 个导出按钮**并给出说明，避免点了没反应；
导入按钮保留。主题交给 Lumina，工具自带的深浅色按钮在插件里隐藏。

### 为什么插件不能触发提取（已核实，不是没做）

读 Lumina 2.0 前端 bundle 得到的事实：

```text
宿主只处理两种 lumina.workshop.* 消息：ready / connect      ← 没有别的模块→宿主通道
模块可达的 RPC 白名单恰好 12 个方法                          ← 没有「提取」类方法
gradient_card / stage_a_parameters / lumina_gradient_card_extract
    在前端 0 命中 → 提取逻辑在 Python 后端，前端走 HTTP
而模块 iframe 的 CSP 是 connect-src 'none'                   ← 模块不能发 HTTP
```

所以「让模块点一下就去跑 Lumina 的梯度卡提取」在 Workshop API v1 里**无法实现**：
既没有对应 RPC，模块也不能调后端 HTTP，更不能写文件到磁盘
（创意工坊 API 里没有「保存文本/二进制文件」这一项）。

### 推荐工作流：一次都不用重新输入

手工测量的数值**就是**梯度卡提取的输出。本工具导出的板面图是按官方几何渲染的
（1340 × 680 px = 67 × 34 mm，20 px/mm，色块中心与官方 `sample_boxes` 逐像素重合），
所以把导出的白/黑底板图**直接丢进 Lumina 的梯度卡提取**，读回来的就是你手填的数值。

1. **填数** —— 独立版手填 36 个色块的 RGB（或用插件版，数据存在模块工程里）
2. **出图** —— 独立版「导出白底板/黑底板」（插件版也可以「交给 Lumina」后在 Lumina 里保存）
3. **提取** —— Lumina「耗材管理 → 梯度卡提取」读这两张图
   > 建议在提取界面上**关闭自动白平衡与亮度校正**（`wb` / `bright`），
   > 否则会把已经准确的数值再"校正"一遍
4. **拟合** —— 「继续拟合 Stage A」→ 得到耗材档案

另一条等价路径（更省步骤，但需要命令行）：

```bash
python tools/lumina_profile_writer.py --measurements 测量模板.csv --brand 品牌 --name 耗材名 --out 档案.zip
```

产出的 ZIP 用 Lumina「耗材管理 → Stage A 耗材档案库 → 批量导入 ZIP」导入即可
（官方文案：`mat_gradient_library_desc`「支持多选导出 ZIP 或批量导入 ZIP」）。

## 宿主真实行为（从 Lumina 2.0 前端 bundle 里读出来的）

官方 SDK 的文档没有写清下面这些细节，是直接读宿主前端实现核实并据此修好的
（Lumina 由本机后端 `http://127.0.0.1:8000/` 提供前端，模块代码在该 bundle 内）：

### 状态机

```text
preparing → loading → handshaking → connected → ready
            ↑ 拉取模块 HTML      ↑ 只有 onLoad 后才「武装」握手
```

宿主用 iframe 的 **`onLoad`** 作为武装时机（`E.current = true`），并起 10 秒超时。
**这意味着模块加载期间发出的 `ready` 会被直接忽略** —— 只发一次必然超时失败。
所以 `workshop/shim.js` 会**周期性重发** `ready`（每 0.8 s，最多 25 次），直到连上为止。

### 端口在 `event.ports` 上，不在 `event.data` 上

宿主这样发：

```js
iframe.contentWindow.postMessage(
  { type: "lumina.workshop.connect", sessionId: crypto.randomUUID() }, "*", [port2]);
```

端口是通过 transfer list 转交的，接收端必须读 **`MessageEvent.ports[0]`**
（官方 SDK 就是 `event.ports[0]`）。

### 宿主发布的主题令牌（真实名字，只有 6 个颜色令牌）

| 令牌 | 浅色 | 深色 |
|---|---|---|
| `--lumina-surface` | `#ffffff` | `#111827` |
| `--lumina-surface-muted` | `#f5f5f7` | `#1f2937` |
| `--lumina-text` | `#1d1d1f` | `#f8fafc` |
| `--lumina-text-muted` | `#6e6e73` | `#cbd5e1` |
| `--lumina-accent` | `#0071e3` | `#0071e3` |
| `--lumina-border` | — | — |

（另有 `--lumina-left-dock-width` / `--lumina-right-dock-width`，不是颜色。）
适配层把上面 6 个映射到本工具的 CSS 变量，并把宿主主题映射到工具的 `.dark` 类。
**在宿主里会隐藏工具自带的「浅色/深色」按钮** —— 主题完全交给 Lumina。

### 宿主注入的 CSP

```text
default-src 'none'; connect-src 'none'; script-src 'unsafe-inline';
style-src 'unsafe-inline'; worker-src data: blob:; img-src data: blob:;
font-src data:; media-src data: blob:; object-src 'none';
frame-src 'none'; base-uri 'none'; form-action 'none'
```

即：**没有任何网络能力**，脚本与样式必须内联，图片只能用 `data:` / `blob:`。
本工具的「零外部资源」正好满足；因此打包脚本里那几条硬性检查不是形式主义。

### iframe 属性

```js
<iframe sandbox="allow-scripts" referrerPolicy="no-referrer" loading="eager"
        srcDoc={runtimeHtml} onLoad={startHandshake}>
```

`sandbox="allow-scripts"`（不含 `allow-same-origin`）→ **不透明源**，
`localStorage` 访问会抛 `SecurityError`。工具的持久化已包在 `try/catch` 里，
宿主内会安全退化为内存保存。

## 修复记录

### v1.1.1（首次真机安装后修）

装上后在宿主里一直显示「正在等待模块就绪」。查真实前端后确认是**两个 bug**：

1. **端口读错位置** —— 写成 `event.data.ports[0]`，正确是 `event.ports[0]`。
   于是 `connect` 被丢弃，模块永远不发 `lifecycle.ready`，宿主状态就停在
   `connected`（文案正是「正在等待模块就绪」）。
2. **`ready` 只发一次** —— 宿主在 iframe `onLoad` 之前会忽略 `ready`，
   只发一次会撞上这个窗口。改为每 0.8 s 重发直到连上。

另外把主题令牌映射改成宿主的**真实令牌名**（原来猜的 `--lumina-bg`/`--lumina-line`
等并不存在），并在宿主模式下隐藏工具自带的主题按钮。

> **测试为什么没抓到**：`tests/workshop_package_test.cjs` 的假宿主原来把端口放在
> `data.ports` 里 —— 照着错误实现写的，于是"验证"了 bug 本身。
> 现在 fixture 按**真实报文形状**（端口在 `event.ports`）发送，
> 并已确认：把旧实现注入回去，测试会失败 3 项。

### v1.1.2（交接被宿主拒绝）

点「交给 Lumina」报 `The Workshop host could not complete the request.`。
这条是宿主 `runHandler` 的**兜底文案** —— 说明 payload 通过了 schema 校验，
是宿主真正干活的 handler **抛了异常**。查宿主代码后确认：

宿主的交接校验里有一组**在 try 之外**的检查，且失败时是 `throw`（`ci()` 就是 `throw`），
所以具体错误码被兜底文案盖住了。规则（容差 `A7 = 1e-6`，几乎必须精确相等）：

```js
recommendedWidthMm  === columns × pitchMm
recommendedHeightMm === rows    × pitchMm
```

本工具的板面图**带边距**：梯度卡两侧各 1 mm（67 mm），而 `6 × 11 = 66 mm` → 被判
`handoff-layout-invalid`；校准板四周各 5 mm，同理不满足。

**修法**：`layout` 是可选字段（源码里 `const e = t.layout; if (e === void 0) return;`），
**省略即跳过该校验**；而且宿主并没有把 `layout` 传给转换器
（`loadWorkshopImageIntoConverter` 只收 `targetWidthMm` / `targetHeightMm`）。
所以本模块**刻意不提供 `layout`**，而不是把 67 mm 谎报成 66 mm 去凑规则。

其余校验本模块本来就满足（已写进测试）：

| 规则 | 值 |
|---|---|
| PNG 头 24 字节 + 签名 + `IHDR` | 由 `canvas.toBlob` 保证 |
| `pixelWidth/Height` 为整数，且与 PNG 的 IHDR 一致 | 取自 `canvas.width/height` |
| 像素数 ≤ 64e6 | 1340×680 = 91 万 |
| 物理尺寸 ∈ [0.5, 9999] mm | 67×34、校准板最大约 235 mm |
| 总厚度 ∈ [0.2, 50] mm | 3.0 |
| `preserveCanvasBounds === true` | 是 |
| `colorLibraryId` 为 `null` 或 ≤256 字符串 | `null` |
| `recipeSource.manifestSchemaVersion === 1` 且 moduleId/版本与当前帧一致 | 是 |
| `projectSchemaVersion`/`renderSchemaVersion` 非空 ≤128 | 是 |
| 配方信封 ≤ 1 MiB | 几百字节 |

> **测试再次修正**：原来有一条断言要求"交接带 3×6 节距 11mm 的 layout" ——
> 那是照着我的错误假设写的。现在测试内置了**宿主全套校验器**
> （`validateHandoffAsHost`，规则逐条抄自真实 bundle），并带一个反例
> （67 mm + 6×11 必须被判违反），确保这类问题不会再溜过去。

### v1.1.3（交接一直卡在「交接中…」）

根因在适配层：导出 PNG 用的是 `canvas.toBlob`，**它的回调在某些沙箱上下文里可能一直不触发**，
而这条路径原先**没有任何超时** —— Promise 永不 settle，按钮就永远停在「交接中…」。
宿主侧已排除（`r9e` 只传两个参数、用内置 `createImageBitmap`；
`loadWorkshopImageIntoConverter` 是同步的 zustand `set`）。

- 改用同步的 `canvas.toDataURL` + 手工 base64→ArrayBuffer，消除悬挂路径
- `handoffCanvas` 整体加 45 秒硬超时（错误码 `CLIENT_HANDOFF_TIMEOUT`）
- 按钮显示已用秒数，失败附带错误码

> 注：工具自己的「导出图片 / 导出 ZIP」路径里仍有两处 `toBlob`（独立版用），
> 插件版里那些按钮已被隐藏，不会走到。

## 如果要改用官方 SDK

`workshop/build.cjs` 目前**不捆绑任何第三方代码**。若将来要按官方指南捆绑
`@lumina/workshop-sdk`，需要：

1. 从官方 Release 下载固定版本的 tarball 并校验 SHA-256
2. 把 `dist/index.js` 内联进构建产物
3. **把模块产物的 LICENSE 换成 GPL-3.0-or-later** —— MIT 可与 GPL 兼容，
   但合并后的产物必须按 GPL 分发；包内 NOTICE 要写明

这是许可层面的决定，不是技术障碍。
